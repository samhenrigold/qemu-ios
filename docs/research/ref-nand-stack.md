# A4 (iPad1,1 / K48AP / iOS 3.2 7B367) NAND stack — findings for a synthetic-NAND generator and an H2FMI model

Scratch artifacts produced (all under the scratchpad, nothing in any repo): `scratchpad/fw/7B367_keys.json` (api.ipsw.me keys), `scratchpad/fw/dec/{DeviceTree.k48ap.bin, iBoot.k48ap.bin, LLB.k48ap.bin, kernelcache.lzss, kernelcache.bin}` (decrypted with openssl; kernelcache LZSS-decompressed, 9,375,730 B, Mach-O), `scratchpad/fw/dec/img3dec.py`, `scratchpad/fw/dec/dtparse.py`.

## 0. Architecture facts that change the plan (read first)

1. **Two different NAND clients, one FIL codebase.** iBoot-817.28 contains the full "Apple NAND Driver (AND) RO" stack (FIL→VSVFL→YAFTL, read-only) and drives H2FMI registers directly (`dec/iBoot.k48ap.bin` strings: `[FTL:MSG] Apple NAND Driver (AND) RO`, `VSVFL Register [OK]`, `YAFTL Register [OK]`, `[FIL] Disable data whitening`, `WMR_CLOCK_GATE called with invalid FMI`). The 3.2 **kernel does not touch H2FMI at all**: NAND goes `AppleNANDFTL (IOFlashStorage-260.11, Whimory/Core/{FPart,VFL/VSVFLInterface.c,FTL/yaFTL.c,L2V})` → `AppleS5L8920XIOPFMI` (kext `com.apple.driver.AppleS5L8920XIOPFMI`, AppleS5L8920X-227.1) → mailbox to the **IOP** running `com.apple.driver.IOP_S5L8930X_firmware` ("EmbeddedIOP for s5l8930x, Copyright 2010, Apple Inc." / "iBoot-817.28", kernelcache.bin offset 0x715200; ARM vector table with `ldr pc` at 0x715000). That IOP firmware is compiled from the same `drivers/apple/h2fmi/{H2fmi_iop.c,H2fmi_read.c,H2fmi_write.c,H2fmi_erase.c,H2fmi_misc.c,H2fmi_dma_iboot.c}` sources whose function names (`h2fmi_read_multi`, `h2fmi_handle_read_ISR_state_machine`, `h2fmi_tx_bootpage_pio`, `h2fmi_wait_dma_task_pending`, `h2fmi_calculate_ecc_bits`, ...) are exactly what openiBoot `plat-a4/h2fmi.c` reverse-engineered (kernelcache.bin 0x721E30–0x7229D8). IOP entry points: `h2fmi_iop_set_config, h2fmi_iop_reset_everything, h2fmi_iop_read_single, h2fmi_iop_read_multiple, h2fmi_iop_write_single, h2fmi_iop_write_multiple, h2fmi_iop_read_bootpage, h2fmi_iop_write_bootpage` (0x72221C–0x7222D0). Consequence: a register-accurate H2FMI model built from openiBoot serves both iBoot and (if the IOP firmware is run on a second CPU, as iEmu did with `cpu_init("cortex-a8")`, `iemu/hw/s5l8930_iop.c:226-268`) the kernel. Alternatively the kernel path can be HLE'd at the IOP mailbox (0x86300000, DT `iop` node `reg = 0x06300000/0x1000, 0x3F300000/0x1000` under arm-io base 0x80000000; IOP VIC at 0xBF300000 in iEmu `s5l8930_iop.c:20`). Exact mailbox opcodes: **NOT FOUND** (needs disassembly of AppleS5L8920XIOPFMI / IOP firmware).
2. **iPad 1 boots from NOR, not NAND.** DT has `arm-io/spi0/nor-flash` with `nvram` (0xFC000/0xFE000 ×0x2000), `diagnostic-data` (0x6000, 0x4000), `raw-device` 0x8000.. (dtparse output); openiBoot iPad1G target adds module `nor-spi` (`plat-a4/iPad1G.SConscript:15-17`) and uses `reserved_blocks = 1` (not 16) for the VFL (`vfl-vsvfl/vsvfl.c:1127-1131`). So there is **no** IOFlashPartitionScheme (`ndrG` page-0 table), no `boot/plog/nvrm/firm` NAND partitions, no effaceable-lockers unit on NAND for this device. The NAND holds only the VFL/FTL "filesystem" area plus special pages.
3. **iOS 3.2 kernel can format NAND itself**: strings `AND: NAND initialisation failed due to format mismatch or uninitialised NAND.`, `AND: Please reboot with reformatting enabled.`, `[WMR:INF] Formatting with metadata whitening`, `[FTL:ERR] FTL_Format failed _EraseAndMarkEC`, boot-arg `nand-enable-reformat` (kernelcache.bin @≈0x4A3888) and iBoot's restore boot-args `rd=md0 nand-enable-reformat=1 -progress` (iBoot strings). The kernel also has a full yaFTL restore (`[FTL:WRN] Recovering NAND Data Structures - this will take some time!`). openiBoot has neither format nor restore (see §3).

## 1. H2FMI register-level behavior (from `openiBoot/plat-a4/h2fmi.c` + `includes/hardware/h2fmi.h`)

Bases: FMI0 0x81200000, FMI1 0x81300000, clock gates 0x27/0x29, IRQs 0x22/0x23 (`plat-a4/includes/hardware/h2fmi.h:4-10`). DT confirms: `flash-controller0` `compatible = "fmi,s5l8920x"`, `reg = {0x01200000,0x01240000,0x01280000,0x01300000,0x01340000,0x01380000} ×0x1000` (arm-io +0x80000000 → 0x81200000 / +0x40000 / +0x80000 for each FMI), `interrupts = 0x22,0x23`, `clock-gates = 0x35,0x37,0x36,0x38`. 16 CE slots (8 per bus, `H2FMI_CE_PER_BUS`, h2fmi.c:347). CDMA data channels: FMI0 data=5, meta=6; FMI1 data=7, meta=8 (h2fmi.c:321-339). The IOP firmware's own debug dump names the registers: `fmi{CFG,CTRL,STAT,INTPND,INT_EN,DBG0..3,DATSIZ}`, `fmc{ON,IFCTRL,CECTRL,RWCTRL,CMD,ADDR0,ADDR1,STATUS,RBB_CFG}`, `ecc{PND,MASK}` (kernelcache.bin IOP region strings). **Sequences** (all in h2fmi.c):
- Reset chip: CE select → CMD=0xFF → RWCTRL=1 → wait 0x40044&1 → W1C (767-778). READ ID: CE → CMD=0x90, ADDR0=addr byte(0), ADDR num=0, RWCTRL=9, wait 0x40044==9 → DATSIZ=0x801, CTRL=3, wait INTPND&2, PIO 8 bytes from 0x14 (795-817), then bus re-init. Chip IDs compared on 6 bytes; the 4-byte `chipID` selects `nand_chip_info` (85-135, 949-961); board id = (num_busses, num_symmetric groups, chip, count, chip2, count) selects `nand_board_info` (137-208) giving **vendor_type** (0x100014 Samsung, 0x120014 Micron, 0x150011 Toshiba) and `nand_timing_info` (210-282). Symmetric-group masks for iPad1G are `{0x3333, 0xCCCC}` (879) = DT `landing-map = 33330000 cccc0000`.
- Read page (DMA, with ECC): `h2fmi_read_multi` (1517-1609): CTRL=6/ON=1/IFCTRL restore (device_reset 474-481); 0x8000C=1, 0x80010=0x1A8 (1134-1138); CFG/DATSIZ/ECCCFG (1167-1172); per page: CE select, ADDR, CMD=0x3000, RWCTRL=0xB, wait 0x40044==0xB (1111-1122); INT_EN=0x100000; wait !(STAT&4) (1339-1372); status poll via `h2fmi_inner_function`: IFCTRL&=~0x100000, RBB_CFG=0x40|0x40<<8, CMD=0x70, RWCTRL=1, wait, INTPND clear, 0x40024=0, RWCTRL=0x50 (581-622) + UNK440=0x20, INT_EN=0x100 → INTPND&0x100 (1253); then CMD=0, RWCTRL=1; INT_EN=2; first page: CTRL=3 and start both CDMA channels (`h2fmi_rw_large_page` 1275-1290: data channel size = bytes_per_page×num_pages, word 4/burst 8, AES ctx; meta channel size = num_pages×**0xA**, word 1/burst 1, no AES); subsequent pages: CTRL=0x82 then 3 (1326-1327) and consume 0x80010/0x8000C (1329-1331, 1221-1249); wait INTPND&2 per page (1420-1445); at end wait DMA completion, cancel channels (1556-1571). Results: 2 = whole page empty, 0x80000025 = all sectors failed, ENAND_ECC (0x24) = uECC (1209-1218, 1587-1600).
- Program page: `h2fmi_write_multi` (1933-1991) → idle handler starts CDMA (same channels, direction=1, AES encrypt ctx) before NAND commands (1883-1896); per page: CE, ADDR, CMD=0x80(/0x81), RWCTRL=9, wait; INT_EN=2, CTRL=5, CMD=0x1000 (program confirm) (1640-1676); wait INTPND&2 then RWCTRL=2 wait 0x40044&2 (652-659); status via 0x70 sequence, fail = STATUS bit0 (1781-1822, 1727-1779). Boot-page (PIO, 3×512 B, no ECC): 661-704.
- Erase block: IFCTRL|=0x200000; CE; ADDR0 = row(block×pages_per_block) packed, ADDR num=2, CMD=0xD060, RWCTRL=0xB, wait 0x40044==0xB; then status poll 0x70 with mask 0x40 (2463-2593); bit0 of status = fail.
- CDMA path (`plat-a4/cdma.c`): controller 0x87000000 (`hardware/dma.h:7`), channel regs at `+ch<<12`: +0 ctrl/status (write 2 = abort/reset 188,411; start = `0x1C0009 | aes_ctx<<8` 305-310; W1C 0x80000 IRQ 441; bits16-17 = running 410; 0x40000 error, 0x100000 spurious), +4 settings (`sep<<16 | wordsize | burst | dir<<1`, 196), +8 txrx register address (must be in table 51-60: 0x81200014/18, 0x81300014/18), +0xC size, +0x14 physical address of 32-byte segment descriptors `{next, flags, ptr, len, iv[4]}` (14-20): flags 3 = data seg, 2 = IV seg, 0x10003/0x30003 data with AES, |0x100 last, 0 terminator (221-298). Channel IRQs 0x30+ch (`dma.h:13`, DT cdma `interrupts` 37 entries starting 0x31?). AES filter contexts at 0x87800000 + ctx<<12: ctrl word `(dma_ch<<8) | 0x20000(dec)/0x30000(enc) | 0x40000(192)/0x80000(256) | 0x100000(custom key) | 0x200000(GID) | 0x400000(UID)`, key words at +0x20..+0x3C (313-398). AES contexts 2..8 are allocated for FMI (327-333).
- Chip-enable/virtual-CE map: CEs are interleaved across buses round-robin (`h2fmi_init_virtual_physical_map` 2679-2716): with 2 chips on each bus, virtual CE0=fmi0:ce0, CE1=fmi1:ce0, CE2=fmi0:ce1, CE3=fmi1:ce1.
- Meta/spare: `meta_per_logical_page = 0xC`, `ecc_bytes (valid meta) = 0xA`, logical page size entry 0 (`nand_some_array` 887, 3072-3074, 3184-3186). Only **10 bytes** go through the meta DMA per page (1286,1621,2410); bytes 10-11 forced to 0xFF after read (2249-2250). **Whitening** is done by the driver, not hardware: XOR the three u32 meta words with `h2fmi_hash_table[(i+page)%256]` (read 2228-2233, write 2388-2401), `page` = physical page number within the CE; table = LCG seed 0x50F4546A, `val = 0x19660D*val + 0x3C6EF35F`, 763 iterations per entry (3220-3232); enabled iff NANDDRIVERSIGN flags & 0x10000 (`vfl.c:175-178`); DT `metadata-whitening = 1`; kernel also has the seed/LCG constants (kernelcache.bin counts: 0x50F4546A ×1, 0x19660D ×2, 0x3C6EF35F ×1). ECC: BCH per 1 KiB sector, bits = f((spare-10)/(page/1024)) via table {0x35→30,0x33→29,0x2C→25,0x1C→16,0x1B→15} (2621-2636) → 30-bit for all iPad parts; the physical OOB/parity layout is never visible to software (controller strips it) — **not needed** by the model or image; the image only needs data + 12-byte meta.
- **iEmu `hw/s5l8930_h2fmi.c` vs openiBoot**: correct: 3 windows (238-270,847-849), CECTRL 0x4000C, CMD byte parsing (0x90/0x30/0x60, 445-486), ADDR0/ADDR1 packing (681-689), 0x40044 = OR of RWCTRL writes (658-675), INTPND bit1 set on CTRL=3 (583-584), 0x1C returns 0x18 (508-509), per-sector ECC FIFO at 0x8000C with 0xA for empty (379-443,713-716), 10-byte meta (404). Wrong/missing: (a) it un-whitens meta inside the controller (430-431) — layering bug; real flash stores whitened meta and the driver XORs, so with a raw dump it double-XORs; (b) no CDMA data path in the FMI model (data served via PIO reads of 0x14; the CDMA channel 5-8 code in `s5l8930.c:752+` pulls from these buffers and applies AES with the segment IV), no program path (`NAND_CMD_WRITE0` unused), erase is a stub (364-377), no 0x80010 summary, no status register semantics beyond 0x80, no timing/CFG effects, IRQs only when `iopEnabled`; (c) image format `ce_N.bin` = 8-byte chip ID + per page (1 flag byte + data + 12 meta) (`iphone-dataprotection/python_scripts/nand/image.py:54-89`), page_size default 4096 — non-sparse, ~65 GB for a 64 GB device. `danzatt/QEMU-s5l89xx-port/hw/s5l8930_h2fmi.c` is byte-identical (`diff -q`).

## 2. On-flash layout

- **Special pages** (`openiBoot/nand.c:83-159`; `nand.py:257-288`): scanned per CE from block `blocksPerCE-1` down to `blocksPerCE - blocksPerCE/10` (nand.py uses /100), pages 0..pages_per_block-1 ascending, first match wins; page data bytes 0-15 = magic NUL-padded to 16 (`"NANDDRIVERSIGN\0\0"`, `"DEVICEINFOBBT\0\0\0"`), payload length u32 at **0x34**, payload at **0x38** (nand.c:142-146; nand.py:253-255). Pages are read through the normal ECC/AES path (`disable_aes=0`), i.e. they are stored **encrypted with the META key** (nand.py:280-286 tries plaintext then META_KEY). Exact block/page on real iPads: **NOT FOUND** (only the scan window). Magics: `NANDDRIVERSIGN` (CE0 only): `sigbuf[0]` epoch char ('1'/'2' accepted for epoch 0), `[1]`='1' ⇒ VSVFL ('0' ⇒ old VFL), `[2]`≤'1', `[3]`='C', `flags = u32 @[4]`, bit 0x10000 = metadata whitening (`vfl.c:121-200`; nand.py:94-97 `nSig, flags = unpack("<LL")`); `DEVICEINFOBBT` (every CE): factory bad-block bitmap, `CEIL(blocks_per_ce/8)` bytes, bit=1 good (`vsvfl.c:829-838, 156-158`); `DEVICEUNIQUEINFO` (SCFG `gfCS`, `firmware/scfg.py`) and `DIAGCONTROLINFO`: only on boot-from-NAND devices (nand.py:260-262); for iPad these live in NOR (DT `nor-flash/diagnostic-data`, iBoot `SysCfg` strings). `EMF!`/`Dkey`/`LwVM` lockers ("kL" `LockerEntry`, `PLog` header, h2fmi.h:175-188; `keystore/effaceable.py`) and `ndrG` IOFlashPartitionScheme (`IOFlashPartitionScheme.py:25-58`: 0x224 `0xDEADCAFE` cemetery, 0x250 `rAps`, 0x35C `sbus`, 0x400 partition table) exist only on boot-from-NAND devices — **not applicable** to iPad 1 (§0.2); the 3.2 kernel has `IOFlashPartitionScheme` code but no `EMF!`/`Dkey` strings (counts 0) and no `AppleEffaceable*`.
- **VSVFL context** `vfl_vsvfl_context_t` (`vsvfl.c:5-35`, mirrored `vsvfl.py:10-39`), 0x800 bytes: 0x000 usn_inc, 0x004 usn_dec, 0x008 ftl_type, 0x00C usn_block (which of the 4 cxt blocks is current), 0x00E usn_page (next page index, stepped by 8), 0x010 active_context_block, 0x012 write_failure_count, 0x014 bad_block_count, 0x016 replaced_block_count[4], 0x01A num_reserved_blocks, 0x01C field_1C, 0x01E total_reserved_blocks, 0x020 field_20[6], **0x026 reserved_block_pool_map[820]** (u16), **0x68E vfl_context_block[4]**, **0x696 usable_blocks_per_bank**, **0x698 reserved_block_pool_start**, **0x69A control_block[3]** (the 3 FTL ctrl blocks), 0x6A0 scrub_list_length, 0x6A2 scrub_list[20], 0x6CA field_6CA[4], **0x6DA vendor_type**, 0x6DE[204], 0x7AA remapping_schedule_start, 0x7AC[0x48], **0x7F4 version (=2 for VSVFL, `vsvfl.py:109`)**, 0x7F8 checksum1 = Σu32[0..0x7F8)+0xAABBCCDD, 0x7FC checksum2 = ⊕u32 ^ 0xAABBCCDD (`vsvfl.c:219-260`; note the accept-if-either quirk 252-259). Storage: the 0x800 context is copied into a zeroed page (396) and written **8 identical times** at pages `usn_page..usn_page+7` of physical block `vfl_context_block[usn_block]` (391-405), spare = `u32 usn_dec, byte[8]=0, byte[9]=0x80 (PAGETYPE_VFL), rest 0xFF` (399-402; spare struct `vsvfl.c:37-60`, `vfl.py:53-62`). Discovery (`vfl_vsvfl_open` 855-941): scan blocks `[reserved_blocks, fs_start_block)` (iPad: from 1; vsvfl.py bounds it to 16 blocks) that are good in DEVICEINFOBBT for a readable page 0, take its `vfl_context_block[4]`; pick the block whose page-0 spare `usnDec` is smallest non-zero; the newest copy is the last readable page at a multiple of 8. Latest cxt across CEs = max usn_inc (645-661); `control_block`, `usable_blocks_per_bank`, `reserved_block_pool_start`, `ftl_type`, `field_6CA` are propagated from it (943-959). Geometry from the NAND layer: `vfl_vsvfl_setup_geometry` 675-802 (`fs_start_block = blocks_per_ce - 27 - reserved - 121*(next_pow2(blocks_per_ce)>>10) + 4 + reserved`, a scan bound only).
- **Vendor type / banks / V2P** (`vsvfl.c:961-1005`, `vsvfl.py:46-65,140-154`): 0x10001 → 1 VFL bank/CE identity map; **0x100014 (Samsung, iPad default)/0x100010/0x120014 → 2 VFL banks per CE**, `pCE = vBank % num_ce`, `pPage = (vPage & (ppb-1)) | 2*(vPage & ~(ppb-1))` and `|= ppb` if `(vBank/num_ce)&1` — i.e. bank0 = even physical blocks, bank1 = odd blocks (74-97); 0x150011 (Toshiba) → 2 banks, `pBlock = 2*vBlock + (vBank%(2n) >= n)` (99-122). `banks_total = num_ce × banks_per_ce_vfl`, `pages_per_sublk = pages_per_block × banks_total` (999-1001), `blocks_per_bank_vfl = blocks_per_ce/2`. Virtual page → physical: `vBank = vpn % banks_total; vBlock = vpn / pages_per_sublk; page_in_block = (vpn % pages_per_sublk)/banks_total`, then bad-block remap and physical-bank address-space adjustment `pages_per_block_2 × (bank_address_space×(pBlock/blocks_per_bank) + pBlock%blocks_per_bank) + page` (197-217; `vsvfl.py:179-188`). `bank_address_space = next_pow2(blocks_per_bank)` when blocks_per_ce not pow2 (h2fmi.c:3137-3155) — for 0x7294D7EC (0x1038 blocks, 1 physical bank) it is 0x2000 but `pBlock/blocks_per_bank` is always 0, so physical page = `128×pBlock + page`. (`vsvfl.py:58-64` has the 0x150011/0x100014 function names swapped — openiBoot is authoritative.)
- **Bad-block / reserved pool**: after open, the DEVICEINFOBBT table is discarded and the BBT rebuilt from `reserved_block_pool_map` (1009-1037): per VFL bank, `poolsize = blocks_per_bank_vfl - reserved_block_pool_start` entries (index `bank*poolsize + i`); value 0xFFF0 = unused spare; `< blocks_per_ce` = the physical block this spare replaces (marked bad); `> 0xFFF0` = the spare itself is bad. `remap_block` (160-195): a bad physical block is replaced by virtual block `reserved_block_pool_start + (k % poolsize)` in vBank `ce + num_ce*(k/poolsize)`. Hence the VFLCxt blocks, and anything in low blocks the FTL must never touch, are entered in the map; the special-page blocks at the top of each CE fall inside the reserved pool (virtual blocks ≥ reserved_block_pool_start) and are never addressed by the FTL because **YaFTL `numBlocks = usable_blocks_per_bank`** (`yaftl.c:100`, `yaftl.py:58`). Map size 820 ⇒ pool ≤ 410 blocks per bank.
- **YaFTL** (`ftl-yaftl/yaftl.c`, `yaftl_common.{h,c}`, `yaftl.py`): geometry `pagesPerSublk`, `numBlocks = usable_blocks_per_bank`, `bytesPerPage`, `total_banks_ftl`, spare size must be 0xC (`yaftl.c:98-117`); `tocPagesPerBlock = ceil(pagesPerSublk*4/bytesPerPage)`, `tocEntriesPerPage = bytesPerPage/4`, `tocArrayLength = ceil(pagesPerSublk*numBlocks*4/bytesPerPage)`, `numIBlocks = 3*ceil((pagesPerSublk-tocPagesPerBlock) - (numBlocks-8), (pagesPerSublk-tocPagesPerBlock)*tocEntriesPerPage)` [sic, 191-194], `totalPages = (numBlocks-8)*(pagesPerSublk-tocPagesPerBlock) - numIBlocks*pagesPerSublk` (198-200), `ctrlBlockPageOffset = nPagesTocPageIndices + nPagesBlockStatuses + nPagesBlockReadCounts + nPagesBlockEraseCounts + 2*nPagesBlockReadCounts + 2*tocPagesPerBlock + 2` (218-240; `yaftl.py:61-79`). Spare `SpareData{lpn u32, usn u32, field_8 u8, type u8, field_A u16}` (`yaftl_common.h:51-57`); types 0x4 INDEX, 0x8 CLOSED, 0x10 LBN (user), 0x20 FTL_CLEAN (ctx), 0x40 MAGIC, 0x80 VFL (17-22). Block statuses 1 ALLOCATED, 2 FTLCTRL, 4 GC(current user), 8 CURRENT, 0x10 FTLCTRL_SEL, 0x20 I_GC, 0x40 I_ALLOCATED, 0x80 I_CURRENT, 0xFF FREE (25-33). **Context** (`YAFTLCxt`, `yaftl_common.h:242-268`; written by `writeCxtInfo` `yaftl.c:316-502`): FTL ctrl blocks = VFLCxt `control_block[3]`; the ctx is a slot of `ctrlBlockPageOffset+1` pages at `block*pagesPerSublk + i*(ctrlBlockPageOffset+1)` (1732-1773; valid slot = first page readable **and** page `slot+ctrlBlockPageOffset` blank; `yaftl.py:97-111`): page0 `"CX01"` header (+4 numIBlocks, +8 totalPages, +0xC latestUserBlk, +0x10 maxIndexUsn, +0x14 latestIndexBlk, +0x18 maxIndexUsn2, +0x1C numAvailable, +0x20 numIAvailable, +0x24 numAllocated, +0x28 numIAllocated, +0x2C numCaches(10), +0x30 field_30, +0x5C tocArrayLength u16, +0x5E tocPagesPerBlock, +0x60 tocEntriesPerPage, +0x62 numFreeCaches, +0x64 field_64, +0x66 pagesUsedInLatestUserBlk, +0x68 pagesUsedInLatestIdxBlk, +0x94 unk188_0x63 (=0x63 = 99% pagesAvailable), +0x95 totalEraseCount), then `tocPagesPerBlock` pages user-BTOC, `tocPagesPerBlock` pages index-BTOC, 1 stats page (YAFTLStats @0, VSVFLStats @0x200, FTLStats @0x400, u32 0x10003 at end-4), `nPagesTocPageIndices` pages of `tocArray[i].indexPage` u32 (0xFFFFFFFF = not on flash), block statuses u8 (CURRENT→ALLOCATED, I_CURRENT→I_ALLOCATED), readCounts u16, eraseCounts u32, validPagesINo u16, validPagesDNo u16; every ctx page has spare type 0x20 and usn = ++maxIndexUsn (`YAFTL_setupCleanSpare` yaftl_common.c:85-89). **Index pages**: type 0x4, `lpn` = TOC page number, data = `tocEntriesPerPage` u32 vpn (0xFFFFFFFF unmapped) (`writeIndexPage` 43-81; lookup `yaftl.py:233-253`). **User pages**: type 0x10, lpn, usn (`initUserSpareDatas` yaftl.c:2200-2215); data AES'd with the FS key keyed by lpn (§4). **BTOC**: last `tocPagesPerBlock` pages of a full block = u32 lpn per page, spare type 0x8 (user) or 0x8|0x4 (index) with block usn (`YAFTL_closeLatestBlock` yaftl_common.c:331-370; entries ≥ max → 0xFFFFFFFF 421-443). "0x1FF" markers are in-RAM L2V only (`L2V_Update(..,0x1FF0002)` yaftl.c:2161), not on flash. Restore semantics (what the kernel's restore does): a block's first page spare type decides user/index, ordered by usn descending (`YAFTL_Restore` 1312-1658, `addBlockToList` 963-1007). Note the yaftl.py `YAFTL_CXT` struct (yaftl.py:10-33) has partially wrong field names; use `yaftl_common.h:242-268`.
- **Partition table**: iOS 3.x uses a plain **MBR** at LPN 0 with two entries; type **0xAE = APPLE_ENCRYPTED** data partition, 0xAF system (`partition_tables.py:56-86`, `nand.py:306-342`: MBR ⇒ iosVersion 3; protective 0xEE + GPT ⇒ iOS 4; LwVM ⇒ iOS 5). openiBoot `bdev.c:100-230` same logic (MBR, GPT if type 0xEE, LwVM magic). The 3.2 kernel contains `IOFDiskPartitionScheme`, `EncryptedMediaFilter`/`EncryptingBlockStorageDevice` (EncryptedBlockStorage-9) and the `tprc`/`TPRC` magic (kernelcache.bin 0x4A2610/0x4A2780), no LwVM strings ⇒ **MBR + 0xAE for 7B367**. Partition sizes: **NOT FOUND** (derive from the 3.2 restore ramdisk's `options.plist`/`asr` layout if needed; single-partition images sidestep it, §4).

## 3. FORMAT capability

- openiBoot: **no VSVFL format, no YaFTL format, no restore**. `vfl_detect`/`ftl_detect` only open (`vfl.c:121-201`, `ftl.c:199-214`); `YAFTL_Restore` starts with `system_panic("yaftl: sorry, no restore + write support yet")` (`yaftl.c:1312-1318`); the only VFL writer is `vsvfl_write_vfl_cxt_to_flash`/`vsvfl_store_vfl_cxt`/`vfl_vsvfl_write_context` which rewrite an already-loaded context (`vsvfl.c:374-495`); YaFTL can write pages/flush a context (`writeCxtInfo` 316-502, `YAFTL_Flush` 620-704, `YAFTL_Write` 2217-2362) only on an already-opened FTL. No `NANDDRIVERSIGN`/`DEVICEINFOBBT` writer exists (grep over `vfl-vsvfl ftl-yaftl nand.c vfl.c ftl.c plat-a4/h2fmi.c`: no format functions).
- iphone-dataprotection: read-only for NAND (all `nand/*.py` only parse; `image.py` opens `O_RDONLY`); `hfs/emf.py` writes only into extracted HFS images (`flagVolume`/`writeBlock`, emf.py:183-201).
- The 3.2 kernel (Whimory FPart/VSVFL/yaFTL in IOFlashStorage-260.11) **does** have `FTL_Format`, VFL format ("Formatting with metadata whitening"), `nand-enable-reformat` boot-arg and yaFTL restore (§0.3). Two viable generator strategies: (A) *full offline image*: write NANDDRIVERSIGN + DEVICEINFOBBT (top blocks, META-key encrypted), 4 VFLCxt blocks per CE (8 copies each) with a consistent pool map/`control_block`, 3 FTL ctrl blocks with one clean `CX01` slot (all fields deterministic from the static layout), index blocks (full closed blocks with BTOC), user blocks (closed, with BTOC) holding MBR + HFS+ pages encrypted with the FS key by LPN, and free blocks erased (0xFF) — the kernel then opens without restore. (B) *minimal + restore*: omit the FTL ctx (leave ctrl blocks erased or `control_block=0xFFFF`) and rely on the kernel's restore scanning block-0-page spares/BTOCs (`YAFTL_Open` 1682-1684 → restore when `control_block[0]==0xFFFF`; kernel restore does exist, unlike openiBoot); riskier because restore also erases/rewrites (needs a working program/erase path in the model). Must-be-valid structures: NANDDRIVERSIGN (+whitening flag consistent with meta), DEVICEINFOBBT bitmaps, VFLCxt (checksums, version 2, vendor_type, map, control_block, usable_blocks_per_bank/reserved_block_pool_start, 8-copy layout, spare usnDec/type 0x80), meta whitening on every non-erased page, per-page AES (META key for everything except FTL user data; FS key for user data), FTL geometry constants exactly as computed by `YAFTL_Init`. Rebuilt/tolerated by the FTL: read/erase counts, stats page contents, TOC caches, L2V, scrub list; `readCount`/`eraseCount` may be 0.

## 4. Encryption

- Hardware path (all in `h2fmi.c:1993-2170`, matching `structs.py:5-6`): every page DMA'd on the data channel goes through a CDMA AES-128-CBC context. Pages inside the region the FTL registers via `nand_device_set_ftl_region(lpn, …)` (yaftl.c:1899, 2239; h2fmi.c:2887-2893) use **FILESYSTEM_KEY** `h2fmi_aes_key_1 = {0x95AE5DF6,0x426C900E,0x58CC54B2,0xCEEE78FC}` = `f65dae950e906c42b254cc58fc78eece`, IV = LFSR of the **LPN** (2×`val = val&1 ? (val>>1)^0x80000061 : val>>1`, 4 words) (`h2fmi_aes_handler_1` 1993-2008; `nand.py:28-36 ivForPage`), one CBC chain per logical page (`dataSize = bytes_per_page`). Everything else (VFL ctx, FTL ctx/index/BTOC, special pages) uses **META_KEY** `h2fmi_aes_key_2 = {0xAB42A792,0xBF69C908,0x12946C00,0xA579CCD3}` = `92a742ab08c969bf006c9412d3cc79a5`, IV = LFSR of the **physical page number in the CE** (`h2fmi_aes_handler_2` 2017-2044). The IOP firmware applies the same (it is the same H2fmi_dma_iboot.c code), so an image must hold ciphertext unless the emulated CDMA-AES special-cases these two keys. The meta (spare) bytes are never encrypted, only whitened.
- iOS 3.x data-partition key: MBR type 0xAE partition; the block at `last_lba-1` of the data partition (read through the FS key like any LPN) starts with `"tprc"`; bytes 4..0x44 are AES-CBC(key 0x89B, zero IV) of `"TPRC" + last-LBA (u64) + ... + 32-byte EMF key + length` (`nand.py:38-45`, `nand.py:334-336`; kernel strings `tprc`/`TPRC` present, EncryptedBlockStorage kext). key 0x89B = AES-256-UID-encrypt of `183e99676bb03c546fa468f51c0cbd49` (`plat-a4/aes.c:11,26-27`; google-code EncryptionKeys wiki); key 0x835 = UID-encrypt of 16×0x01 (aes.c:10,23-24). The data volume is then AES'd per 4 KiB block with the EMF key, IV = LFSR(LBA + partition offset) (`emf.py:122-133`, `carver.py:108`). No effaceable area, no per-file `com.apple.system.cprotect` in 3.2 (kernel string count 0). The iOS 4-style lockers (`EMF!`, `Dkey`, `LwVM` in a `kL` PLog; openiBoot reads them from NOR at 0xFA000 for iPad, h2fmi.c:2911-2948) are irrelevant for 3.2.
- Emulator choices: (i) since the emulator owns the UID key, the generator can compute key89B and emit a `tprc` block + EMF-encrypted data volume; (ii) simpler: **one MBR entry of type 0xAF holding a single HFS+ root** (as `qemu-ios/imgtools/build_nand.py` does for the iPod: rewritten `/private/etc/fstab`, root rw), which avoids EMF/0x89B entirely. The system partition is "encrypted" only at the FTL layer (FS key, above) — the kernel never applies EMF to it.

## 5. Geometry and shrinking

- iBoot-817.28's own tables (`dec/iBoot.k48ap.bin` +0x29234 chip table, 9×28 B; +0x29330 board table, 17×24 B; timing at +0x294E0) are identical to openiBoot's `CONFIG_IPAD_1G` tables (`h2fmi.c:120-130, 183-200, 257-274`): supported chips {0x7294D7EC, 0x72D5DEEC, 0xB614D5AD, 0x2594D7AD, 0x3294E798, 0x3294D798, 0x3295DE98, 0x3295EE98, 0x4604682C}; board configs always 2 buses (except one 1-bus Hynix SLC dev config) with 2 symmetric groups of 2 or 4 CEs each, i.e. **4 or 8 CEs**. iFixit/Chipworks: retail 16 GB Wi-Fi iPad = two Samsung **K9LCG08U1M** 8 GB packages ([iFixit](https://www.ifixit.com/Teardown/iPad+Wi-Fi+Teardown/2183), [Chipworks via GlobeNewswire](https://www.globenewswire.com/news-release/2010/04/05/1336798/0/en/Chipworks-Teardown-of-the-iPad-Reveals-Few-Changes-in-State-of-the-Art-Semiconductor-Technologies.html)); Toshiba dual-sourced. Matching entries: **16 GB = 4 CE × ID 0x7294D7EC: 0x1038 (4152) blocks/CE × 128 pages × 8192 B, spare 0x1B4 (436), 1 physical bank, vendor 0x100014, 2 VFL banks/CE → banks_total 8, pages_per_sublk 1024, ~16.2 GiB data**; 32 GB = 8 CE × 0x7294D7EC (board[2]); 64 GB = 8 CE × 0x72D5DEEC (0x2070 blocks, 2 physical banks, bank_address_space 0x2000) (board[3]); Toshiba equivalents 0x3294E798 ×4/×8 (0x1004 blocks, spare 0x1C0) and 0x3295EE98 ×8 (0x2008 blocks, 2 banks). ECC = 30-bit/1 KiB for all. Raw dump size 16 GB model ≈ 17.1 GiB; data+12 B meta ≈ 16.2 GiB. CE→bus interleave per §1. The kernel gets geometry from DT `flash-controller0/disk` props that iBoot fills (`#ce, #ce-blocks, #block-pages, #page-bytes, #spare-bytes, device-readid, vendor-type, bbt-format, #databus, #die-ce, ecc-threshold, ecc-correctable, *-ns timings, metadata-whitening, landing-map, default-ftl-version=1`; all zero in the static DT, dtparse output) and then re-probes via the IOP (`AppleS5L8920XIOPFMI: Found Chip ID ... on FMI%lu:CE%lu`, `NAND device ID 0x%08llX in map 0x%08lx %llu-bus not supported`, `iVSVFLBankNum!=_fmiBankCount`) — so **the emulated chip ID must be one of the 9 IDs above with a CE count/bus placement matching a board entry**; blocks_per_ce cannot be shrunk for a given ID.
- Shrinking options: (a) present a small real ID: **0xB614D5AD (SLC, 0x1000 blocks × 128 × 4096 B, spare 0x80)** ×4 CE on 2 buses (board[15]/[16], vendor 0x100014) → 8 GiB logical, `pages_per_sublk = 128×8 = 1024`, same 4 KiB page size as the iPod image; or 0x2594D7AD ×4 (16 GiB, 4 KiB pages). (b) keep 0x7294D7EC and store the image sparsely (qemu-ios `pack_nand.py` index format already maps only present pages; erased pages read as 0xFF) — a 3.2 rootfs (018-7223-007.dmg, ~600 MB) touches <1 GB of pages. Either way the model does not need a full-size backing file. Unlike the iPod (`ipod_touch_fmss.h:17-21`: 4096+64 B pages, 128 pages/block, 4 CS × 4096 blocks as the task states), the iPad image needs 8192-byte pages (or 4096 with the Hynix/Micron IDs) and only 12 spare bytes per page.
