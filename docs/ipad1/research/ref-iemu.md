# Audit: cmw's iEmu S5L8930 / ipad1g machine (and winocm's QEMU-s5l89xx-port)

## 0. Provenance and scope facts

- The two trees are **byte-identical in `hw/`**; `diff -rq` over the whole tree (excluding `.git`) reports only `README` differs and `README.md` exists only in teknogeek/iemu. Both are one-commit repos with no mineable history: danzatt = `919b455 cmw Thu Aug 30 19:15:23 2012 -0400 "more changes"`; teknogeek = `ee50286 John Smith (awesomebing1) 2015-03-11 "And I've moved the wiki again"`. GitHub code search shows the same `hw/s5l8930*.c` files copied verbatim into `userlandkernel/iDeviceEMU` (`Main/linux/hw/`), `MTJailed/iDeviceEmulator`, `aquynh/iVM`, `PWagner1/…`, `DJHartley/…` — no independent continuation found.
- Base QEMU is ~0.14 (2011 API: `cpu_register_io_memory`, `CPUReadMemoryFunc`, `qemu_mallocz`, `SysBusDeviceInfo`, `target_phys_addr_t`). Build wiring: `Makefile.target:361-364` (`s5l8930.o s5l8930_i2c.o s5l8930_i2cchg.o s5l8930_spi.o s5l8930_iop.o pflash_spi.o s5l8930_h2fmi.o ipad1g.o`, plus `usb_synopsys.o pcf50633.o s5l8900_uart.o pl192.o`), `Makefile.target:231 tcp_usb.o`, `Makefile.objs:173 iemu.o`, `--enable-skinning` in `configure:728`. Links `-lexpat`, OpenSSL (`s5l8930.h:5-6`).
- Run line (README.txt): `qemu-system-arm -M ipad1g -option-rom iBoot.k48ap.RELEASE.unencrypted -global s5l8930_h2fmi0.file="0,ce0.bin;2,ce2.bin" -global s5l8930_h2fmi1.file="0,ce1.bin;2,ce3.bin" -pflash ipadnor.bin -gdb tcp::6666 -nographic -S -serial file:serial.txt -monitor stdio -smp 2`.
- **The actual target was iPad1,1 on iOS 4.3.5 (8L1), not 3.2.** `kernKey435`/`kernIV435` (`s5l8930.h:101-102`) = ipsw.me iPad1,1/8L1 Kernelcache key `1652c859…ccdd` / IV `80f4c70d…21eb`; `deviceKey435`/`deviceIV435` (`s5l8930.h:103-104`) = 8L1 DeviceTree key `c699afb2…6f30` / IV `2a3c0a12…f3d1` (https://api.ipsw.me/v4/keys/ipsw/iPad1,1/8L1). The `Key835`/`Key89B` constants (`s5l8930.h:99-100`) are the well-known iOS key-0x835/0x89B derivations (unused, commented at `s5l8930.c:714-725`).
- `iemu.c`/`iemu.h`: an expat parser for `devices/<name>/config.xml` (`device/hwid/skin/boot/loadaddr`), only `devices/iPhone1/config.xml` exists (`hwid m68ap, boot iboot, loadaddr 0x18000000`); `iemu_fw_init` is a no-op stub (`iemu.c:91-98`). `skin/` is the Nokia QEMU skinning code (`skin_config.c:1-5`, GPL, 2009 Nokia) — cosmetic PNG bezel + buttons, not iPad-specific. Nothing here is relevant to hardware.

## 2. The IOP (`hw/s5l8930_iop.c`, 270 lines)

- **It is a second `cortex-a8` TCG CPU, not an ARM7** (`s5l8930_iop.c:227`), with its own set of 4 chained pl192 VICs at **0xBF300000** stride 0x10000 (`:18-21, 237-252`). This matches the 3.2 DeviceTree `arm-io/iop`: `reg = 0x06300000/0x1000, 0x3f300000/0x1000` (i.e. 0x86300000 control + 0xBF300000 IOP VIC), `interrupts = 3`, `compatible iop,s5l8930x / iop,s5l8920x`, `iop-version 2` (dt.txt:838-849).
- Control block at 0x86300000: write `0x110` = IOP start address; write `0x100` bit0 → `cpu_interrupt(main, CPU_INTERRUPT_HALT)` and `run_on_cpu(iop, do_iop_run)` which sets `iop->regs[15] = startaddr`; bit4 = stop (`:80-104`). `0x18/0x1c/0x24` are accepted silently; everything else logs "UNKNOWN". The IOP→AP doorbell IRQ 3 is captured (`:261`) but `iopTriggerIRQ` is empty (`:212-216`). Cross-CPU handoff hacks in pl192 are all `#if 0` (`pl192.c:128-135, 390-408`), so after start the main CPU only resumes when a VIC0 interrupt clears `halted`.
- `do_iop_run` also **patches 16 bytes at physical 0x40762790 with Thumb `0x2000` (MOVS r0,#0) "to fix some power gate init issue @ pmgr_enable_gates"** (`:57-62`) and re-points CDMA channels 5-8 IRQs (0x35-0x38) from VIC0 to the IOP's VICs (`:64`, `replaceCDMAIRQHandlers` `s5l8930.c:926-933`). H2FMI IRQs 0x22/0x23 are wired to the IOP VIC from the start (`s5l8930.c:1484-1485`, `getH2FMI_IRQ_0/1` `:202-210`). The IOP is created halted (`:269`).
- IOP RAM: 1 MiB of RAM at 0x0 named `iopram.ram` (`ipad1g.c:431-432`). The IOP PC is set to the *physical* start address written by the AP; no remap of 0x0 is modelled.
- **Who uses the IOP:** not iBoot. iBoot-817.28 (`dec/iBoot.k48ap.bin`, link base 0x5FF00000 from vector literal `5ff00040` at file offset 0x20) contains **zero** literals for 0x86300000 or 0xBF300000 and its NAND driver is the in-iBoot path (`drivers/apple/h2fmi/H2fmi_dma_iboot.c`, `h2fmi_dma_execute_async`, `cdma_init()`, `aes_hw_crypto_cmd` strings in `dec/iboot.str`), driving H2FMI + CDMA directly from the AP. The **3.2 kernel does require it**: kernelcache kexts `com.apple.driver.AppleS5L8920XARM7M` (host driver: "IOP: startup ping failed", "EmbeddedIOP firmware %s-%s %s", maps `mapDeviceMemoryWithIndex(0)` = 0x86300000 and `(1)` = the IOP VIC, "arm7m version %d not supported", "IOP panic"), `AppleS5L8920XIOPFMI` (NAND over IOP mailbox, `h2fmi_iop_read_single/multiple/bootpage…`), `AppleS5L8920XIOPSDIO`, and `com.apple.IOP_S5L8930X_firmware` carrying the firmware blob ("EmbeddedIOP for s5l8930x, Copyright 2010, Apple Inc.", `iBoot-817.28`) — `fw/7B367-dec/*.kext.bin`, `iop_firmware_section.bin`. The firmware entry is **ARM32** (`ea00000e` + `e59ff018` vectors, link base 0 with vector literal 0x40 at +0x20), so running it on a Cortex-A8 TCG CPU is ISA-compatible. The 0x40762790 NOP patch sits inside kernel RAM, i.e. inside the kernel-allocated IOP firmware copy → strong evidence cmw's 4.3.5 kernel reached `AppleS5L8920XARM7M::start`, loaded the IOP firmware, and it wedged in its PMGR gate-enable loop (inference).
- Conclusion for us: **the 3.2 kernel's NAND, SDIO (and therefore rootfs mount) go through the IOP mailbox.** The only two ways are (a) run the EmbeddedIOP firmware on a second CPU with a faithful mailbox/VIC/PMGR model (iEmu's approach, never finished), or (b) replace `AppleS5L8920XIOPFMI` traffic with a host-side fake IOP that answers the message protocol. openiBoot never uses the IOP (`plat-a4/h2fmi.c` is AP-driven; only comments mention IOP at `includes/h2fmi.h:88-117`).

## 3. How far it got, and the bypass hacks

- No commit log to mine (see §0). Public record (search snippets only; wiki pages themselves were unreachable): Kickstarter "iEmu: an open-source iOS device emulator" by Chris Wade, Aug 17–Sep 16 2011, $20,442 / $20,000, 165 backers; abandoned ~2013; iEmu → Virtual → Citrix → Corellium. The iPhone Wiki snippet says "CMW got as far as getting the iPad 1 … kernel booting"; I could not verify the iOS version claim.
- Code evidence of reach: (1) iBoot ran far enough to pull the **kernelcache and DeviceTree out of NAND** (FTL/VFL parsed by iBoot from the ce dumps) and pass them through GID-AES — hence the size-keyed decryption hack; (2) the kernel ran far enough to start the IOP (the `0x40762790` patch); (3) `KERNStart 0x80000000` (`s5l8930.h:12`); (4) SDIO IRQ kludge in the CE-ATA stub (`s5l8930.c:1341-1343`) suggests the kernel's SDIO probe was being coaxed. No serial logs, screenshots or panics are in either repo.
- Hacks/bypasses:
  - **GID AES**: `AESGID` → "We cant do anything here as we dont know the GID key" (`s5l8930.c:676-679`), then decrypts by *plaintext size*: `0x5e42c0` → 8L1 kernel key/IV, `0xe9a0` → 8L1 DeviceTree key/IV, otherwise whatever key was last set with zero IV (`s5l8930.c:700-713`). UID key is a constant `01 23 45 67 89 AB CD EF ×2` (`s5l8930.h:97`). Every AES op **writes `/tmp/aes/inbuf-N.img`, `key-N.img`, `outbuf-N.img` with unchecked `fopen`** (`s5l8930.c:696-739`) — crashes if `/tmp/aes` is missing.
  - **SHA-1 returns zeros** (§1) → any signature/hash check must have been defeated by patching the "unencrypted" iBoot image supplied via `-option-rom` (not verifiable; no patch script in repo).
  - iBoot entered directly at 0x5FF00000 with PC set (§4): no SecureROM, no LLB, no Image3 parsing of iBoot itself.
  - CDMA `CDMASTS` always 0x18 "DMA done" (`s5l8930_h2fmi.c:508-509`); erase is faked (`:364-377`); ECC status is always "ok/empty"; PMU/charger read 0xff; GPIO board-id pins forced to 1; misc-sys constants; USB hwcfg garbage.

## 5. Input file formats

**NOR (`-pflash ipadnor.bin`)**: raw 1 MiB image read with `bdrv_read` (`pflash_spi.c:694`); 4 KiB sectors; served only via SPI0 command 0x03 with 24-bit address; JEDEC 1F 45 02. Contents expected = real device NOR dump (Image3 LLB/iBoot/logos + NVRAM), which iBoot's `flash_spi`/`nvram` code reads (`dec/iboot.str` `flash_spi_*`, `nvram_save`). Writes are unsupported so NVRAM saves fail.

**NAND (`-global s5l8930_h2fmiN.file="ce,path;ce,path"`)** (`s5l8930_h2fmi.c:272-334`): one file per CE; property defaults `page_size 4096, meta_size 12, ecc_shift 10` (→ `ecc_stages = 4`), `fmtn` 0/1 (`:806-832`). Layout (`:216-227, 353-443`):
```
offset 0      : 8-byte NAND chip ID (returned for READID 0x90)
offset 8 + page*(1 + page_size + meta_size):
    byte 0    : marker; 0x00 or '0' = erased/empty (ECC status 0xa), else programmed
    +1        : page_size data bytes
    +1+psize  : meta bytes (only meta_size-2 = 10 are read; first 3 words are de-whitened
                by XOR with h2fmi_hash_table[(i+page) % 256], table seeded 0x50F4546A,
                LCG 0x19660D/0x3C6EF35F ×763 per entry, `:22-38,430-431`)
```
`page` = row address assembled from ADDR0 (`>>16`) and ADDR1 (`<<16`) (`:681-689`); CE = `ffs(CHIP_MASK)-1` (`:206-214`). Commands parsed byte-wise from NCMD (`:479-486`): 0x90 READID, 0x30 READSTART, 0x60 ERASE (fake), 0x00 ignored; data through DATA0 (0x14, 1/2/4-byte reads), meta through DATA1 (0x18), ECC results 4 bytes × stages via ECC +0xC. The DT `nand` node shows `metadata-whitening = 1`, `landing-map 0x3333/0xcccc` (dt.txt:292-315) and `flash-controller0 reg` = 0x81200000/0x81240000/0x81280000 + 0x81300000/… (dt.txt:272-282) — i.e. the true sub-block offsets are 0x40000/0x80000, matching iEmu and openiBoot `hardware/h2fmi.h`. The tool that produced these marker-byte dumps is not in the repo (likely an openiBoot `nand` dump variant) — **not found**.

## 6. LCD

- `ipad1g_clcd_init(0x89100000)` maps 0xFFFF of MMIO; **reads return 0; any write logs and sets `frame_base = 0x4F700000`** (`ipad1g.c:243-266`, `CLCD_FRAMEBUFFER` `ipad1g.h:14`); the "window 2 framebuffer at offset 0x78" idea is commented out (`:258-265`). Display is refreshed by `framebuffer_update_display` at fixed 1024×768, 16 bpp RGB565 (`switch(4)` → `draw_line_table16`, `:178-229`). No registers modelled at all.
- This is wrong for the iPad: per the 3.2 DT, `clcd reg = 0x89000000/0x7000 (display pipe 0) + 0x89200000/0x2000 (CLCD)`, `rgbout reg = 0x89100000 (pipe 1) + 0x89600000`, `mipi-dsim 0x89500000`, `lcd,pinot` panel (dt.txt:919-982). iBoot-817.28 literal scan: 0x89000000 ×2, 0x89200000 ×1, 0x89500000 ×3, **0x89100000 ×0**, framebuffer **0x5F700000 ×3 (not 0x4F700000)**. openiBoot's iPad build uses `DISPLAY_PIPE0 0x89000000` and `CLCD_FRAMEBUFFER 0x4F700000` (`plat-a4/includes/hardware/clcd.h:4-17`; 0x5F700000 only for iPhone 4 — but Apple's 3.2 iBoot uses 0x5F700000 on K48 because of the DRAM mirror). Register sequence that a real model needs is in `plat-a4/clcd.c:260-324`: pipe `+0x104C` (DPCPFDMA bits), `+0x1030` = width<<16|height, `+0x205C/+0x2060/+0x105C/+0x2064`, window regs `+0x4040`; CLCD `+0x00` reset 0x100, `+0x14/+0x18`, VIDCON1 `+0x54`, VIDTCON `+0x58/+0x5C/+0x60`, window enable `+0x34/+0x38`. iEmu contributes nothing usable here.

## 7. Cross-check against the 3.2 DeviceTree (K48AP, `dec/dt.txt`) — addresses iEmu got right/wrong

Right: VIC 0xBF200000 stride 0x10000; GPIO 0xBFA00000; PMGR base 0xBF100000; CDMA 0x87000000 + AES 0x87800000; SHA1 0x80100000; FMI 0x81200000/0x81300000; SPI0 0x82000000 IRQ 0x1d; UART0 0x82500000 IRQ 0x16; I2C0 0x83200000 IRQ 0x13; USB PHY 0x86000000; USB device 0x86100000 IRQ 0xd; IOP 0x86300000 + 0xBF300000 IRQ 3; CDMA channel IRQs 0x31…; H2FMI IRQs 0x22/0x23; CE-ATA 0x81000000. Wrong/short: PMGR size (0x1000 vs 0x6000 → clock-gate regs unmapped), CDMA size (0x10000 vs 0x26000), LCD base and framebuffer, chip-ID window (0xF), no SDIO (0x80000000), no PKE 0x83100000, no SGX 0x85100000, no AMC 0x84100000, no swi 0xBF600000, no watchdog.

## 8. Frank reusability assessment for QEMU 8.2

- **Code: essentially zero direct reuse.** Every device uses the 2011 `cpu_register_io_memory`/`CPUReadMemoryFunc`/`SysBusDeviceInfo`/`qemu_mallocz`/`cpu_physical_memory_*` API and global singletons (`s5l8930`, `IOPState`, `base_addr`, `intnum`); nothing compiles against `MemoryRegionOps`/QOM. The devices are also shallow (most are log-and-return-constant stubs) and carry hard crashes (`/tmp/aes` dumps, SPI1-4 NULL pflash, USB arity bug).
- **Facts worth harvesting (≈ a day of rewrite each, verified against the 3.2 DT above):** chip-ID triple and epoch bit positions; PMGR PLL/prediv/base constants that a 4.3.5 iBoot accepted (likely close for iBoot-817, since both parse the same PLL_CON layout at +0x0/+0x8/+0x10/+0x20); the timer/POWER_ID register set (0xBF102000 window, +0x4000 = 0x2020001); GPIO board-id offsets 0x9c/0xa0; CDMA per-channel register layout (`chan<<12`: status/config/txrx/size, 0x14 segment list, bit19 done) and the AES filter setup/IV/key offsets — cross-validated by openiBoot `plat-a4/cdma.c:187-198, 302-310, 341-393, 430-446` and `hardware/dma.h`; the H2FMI three-window layout and NCMD/ADDR/CHIP_MASK/DATA/ECCBUF offsets (cross-validated by `plat-a4/includes/hardware/h2fmi.h`); the metadata-whitening LCG; the SPI-NOR command handling; the IOP control-word semantics (0x100 bit0 start / bit4 stop, 0x110 start address) and the fact that IOP interrupts come through a second pl192 bank at 0xBF300000.
- **Prefer as references instead of iEmu:** openiBoot `plat-a4/` (`cdma.c`, `h2fmi.c` ~1100 lines, `clcd.c`, `clock.c`, `gpio.c`, `spi.c`, `usbphy.c`, `pmu.c`) is more complete and was written by the same people (ricky26/Bluerise) against real hardware; and our own qemu-ios S5L8720 devices for the QEMU-8.2 shape (SPI/UART/I2C/pl192 are the same IP families).
- **Design lessons iEmu teaches:** (1) iBoot-817 only needs AP-side H2FMI+CDMA+AES+SHA1+SPI-NOR+UART+timer+VIC+chipid/PMGR/GPIO to reach recovery/kernel load — the IOP can be deferred until the kernel; (2) the kernel cannot mount the rootfs without the IOP mailbox protocol being served (either run EmbeddedIOP on a second CPU with a real PMGR/VIC model, or fake the `AppleS5L8920XARM7M` message ring host-side); (3) the DRAM mirror (256 MiB visible at both 0x40000000 and 0x50000000; iBoot linked at 0x5FF00000, framebuffer 0x5F700000) must be modelled as an alias, not by faking 512 MiB; (4) GID-AES is the hard wall for any Image3 we don't already have decrypted — the ipsw.me 7B367 keys cover iBSS/iBEC/iBoot/LLB/Kernelcache/DeviceTree/logos/ramdisks (https://api.ipsw.me/v4/keys/ipsw/iPad1,1/7B367), so a size- or tag-keyed "GID oracle" like iEmu's is viable for a fixed build.
